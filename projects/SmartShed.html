01 · 系统架构与总览

Smart Shed（智慧大棚）贯穿嵌入式硬件感知、MQTT 公网消息路由以及 HarmonyOS 多形态终端：两块板卡在硬件隔离与逻辑解耦的前提下，围绕温湿度、光照和土壤水分实现持续监测与自动调控。

DEVICE · 嵌入式端

OpenHarmony 1.0 Release

运行 Rayawa/rgb 与 Rayawa/soi 两套 HiSilicon Hi3861 节点：前者统筹空气温湿度与光照感知和补光，后者负责土壤湿度采集与水泵/风扇 PWM/GPIO 执行。

工程实践中遇到的核心难点

难点 1 嵌入式端协调 驱动接口随版本演化存在兼容性差异；AHT20 与 OLED 共享同一条 I²C 总线时的并发冲突排查耗时长；LiteOS-M 多线程栈大小与优先级需要反复调优。
难点 2 应用端现代化重构 旧版文档基于早已过时的 API7 JavaUI，且旧代码硬编码适配特定型号平板导致换机即布局错乱；原本扩展板“一板一外设却设四套体系”造成较大规模的重构工作量。
难点 3 通信链路稳定性 实际联调过程中暴露出 MQTT 报错不透明、Hi3861 老化 Wi-Fi 模块高负载稳定性下降，以及旧版应用侧收发逻辑缺少错误处理、调试全靠猜的问题。

方案创新点

双板分离架构

环境感知板（RGB）与土壤执行板（SOI）实现物理隔离与职责解耦，各自专注对应外设并在云端协同工作。

零依赖 MQTT 客户端

HarmonyOS 端彻底摒弃第三方 MQTT 封装库，直接从 TCP Socket 底层字节流手写实现完整报文解析与连接保活。

HDS 高级视觉体系

引入鸿蒙官方 Design System 组件体系，集成沉浸式导航、按压引力动效及流动光场背景。

手动 / 智能双模式

手动模式允许随时拖拽调节各执行器挡位；智能模式则由常驻后台线程依据四维阈值自动触发设备调控。

Glass 手表形态适配

额外扩展手表端 Glass 形态界面，融合沉浸式材质与轻盈气态过渡动效。

多层级可靠性保障

建立 5 秒离线超时自动探测、断线指数退避重连及 GlobalLogBus 全局事件日志总线进行全链路兜底。

02 · MQTT 发布订阅与数据流

选用面向低带宽物联网环境设计的轻量级 MQTT Pub/Sub 协议，解耦硬件节点与移动端之间的直接网络依赖。

PUBLISHER

发布者（Hi3861 节点）

嵌入式端定时将采集得到的环境与土壤参数封装成标准 JSON 消息，发布至约定的上报 Topic。

BROKER

EMQX 消息中转站

EMQX 接收各方报文后，严格依照主题层级与路由策略完成高效分发转发。

SUBSCRIBER

订阅者（HarmonyOS App）

手机应用订阅遥测 Topic 获取实时状态曲线，并在用户或规则触发时逆向推送控制命令。

上行链路：传感器数据 → 手机显示

  1. 传感器采样：ADC 读取光照与土壤湿度，I²C 读取 AHT20 空气温湿度。
  2. JSON 打包发送：Hi3861 序列化数据，经 MQTT PUBLISH 报文送往 EMQX Broker。
  3. Topic 路由分发：EMQX 将消息推送给所有已订阅对应通道的移动客户端。
  4. 界面响应式刷新：应用解析载荷并更新 @StorageLink 状态，驱动界面数字刷新与智能模式阈值比对。

下行链路：控制操作 → 硬件执行

  1. 操作或自动触发：用户在手动模式调节挡位滑块，或智能模式因参数越界自动产出调控指令。
  2. 报文下发中转：HarmonyOS 客户端将控制指令拼装为 MQTT 报文经由 EMQX 分发。
  3. 板端解析执行：Hi3861 接收后解析主题与内容，写入目标变量驱动 GPIO / PWM，动作风扇、水泵或补光灯。

03 · Hi3861 嵌入式端实现

纯 C 语言基于 OpenHarmony LiteOS-M 与 CMSIS-RTOS 多线程架构开发，目录分为公共支撑层 common/、业务外设层 modules/ 与按板条件编译构建层 boards/。

RGB 板（环境感知与补光）

负责“观测量环境参数”与“本地补光状态显示”：

  • 传感器：AHT20（I²C 读取空气温湿度）、光敏电阻（ADC 读取光照强度 0~4095）。
  • 执行与显示：RGB 三色灯（GPIO10/11/12 => PWM1/2/3 无级调光），SSD1306 OLED（128×64）实时刷新读数。

SOI 板（土壤监测与执行器）

负责“土壤水分监测”与“机械执行器控制”：

  • 传感器：土壤湿度探头（替换安装于扩展板，经 ADC 采样土壤水分变化）。
  • 执行与显示：PWM 风扇调速、GPIO 水泵开关控制，配合板载 OLED 实时打印状态日志。
DIR 1 common/ 公共层 集中放置 Wi-Fi 连网、MQTT 通信封装、OLED 驱动以及用于防并发抢占的 I²C 总线互斥锁。
DIR 2 modules/ 业务层 细分为 sensors/（AHT20、光强、土壤湿度源码）与 actuators/（风扇、补光灯、水泵控制模块）。
DIR 3 boards/ 构建层 统一管理两块板卡的 .gn 构建描述文件，条件编译按需激活模块，扩展新节点只需新增对应 gn 配置。

多线程调度：smart_shed_all.c（SYS_RUN 主入口 · 8KB 栈）与六子线程

主线程依据条件编译配置拉起以下六个独立任务，各子线程具备 4KB~8KB 独立栈空间与优先级，彼此并行互不阻塞；针对 AHT20 与 SSD1306 共用 I2C0（GPIO13 & GPIO14） 的并发错乱问题，引入 i2c0_lock / unlock 互斥锁保障同一时刻仅单个外设占用总线。

AHT20 / I²C 周期读取与互斥锁保护

04 · HarmonyOS 移动应用端（Smart Shed App）

采用 HarmonyOS 6.1.0 (API23) Stage 模型与 ArkTS 开发，全面适配 Mate 70 Pro+ 手机（单栏流式卡片）与 MatePad Pro 平板（自适应双栏布局）及手表 Glass 形态。

手动精准调控

支持拖拽滑块调节风扇（0–3 档）、水泵（0–3 档）及补光灯（0–100%），进入页面自动向开发板同步状态并配合触觉反馈。

智能模式与自动决策

预设温度、湿度、光照与土壤湿度上下限阈值，后台常驻轮询线程在数值越界时自动触发控制指令，退出页面时安全销毁防内存泄漏。

实时数据监控

MQTT 异步回调收到新消息后，通过 @StorageLink 状态绑定驱动 ArkUI 界面自动无感刷新。

GlobalLogBus 调试面板

内置事件总线完整采集通信收发状态、用户控制行为与异常报错，便于直接在移动端排查现场问题。

Stage 1AppScope/应用级全局配置资源与 Hvigor 构建管理入口。
Stage 2view/ & pages/基于 ArkTS 与 HDS（HdsNav 沉浸导航、PressShadow 引力按压、SpringMotion 弹簧曲线、流光光场与引力转场）构建的响应式 UI 层。
Stage 3service/封装自研 MqttReceiverClient.ts，基于原生 TCP Socket 手写 MQTT 报文编解码实现可靠双向通信。
Stage 4viewmodel/集中管理设备控制挡位（@StorageLink / @ObjectLink）与跨页面共享状态模型。

MqttReceiverClient.ts · 协议层自主掌控

  • 直接由 TCP Socket 手工拼接 Fixed Header + Variable Header + Payload
  • 自主实现 CONNECT / PUBLISH / SUBSCRIBE / PINGREQ 核心报文
  • 内置 60 秒 KeepAlive 心跳保活，通过 MQTT 5.0 over WSS 直连 EMQX 公网 Broker

可靠性保障与生命周期管理

  • 支持断线自动重连与指数退避重试，避免频繁无效建连拖垮资源
  • 单条 TCP 链路支持多 Topic 订阅路由分发并与 ArkUI 表现层解耦
  • 进页面建连、退页面主动销毁定时线程与句柄，结合 GlobalLogBus 杜绝泄漏与排查盲区

Smart Shed Glass（手表形态）

围绕小尺寸表盘构建了沉浸式玻璃质感材质与轻盈气态动效，保留双边缘流光与引力转场视觉语言。

HdsButtons 自定义交互控件

遵循 HDS 设计规范封装不同尺寸及默认 / 按压 / 禁用态样式的自定义按钮族，保证小屏表盘上清晰可读、精准可点。

05 · 常见问题与项目总结

工程技术选型反思、六周开发复盘以及作为完整课程原型落地边界的坦诚整理。

为什么选择 OpenHarmony，而不是 Arduino / ESP32？

OpenHarmony 提供真正的 RTOS（LiteOS-M），具有抢占式调度、原生多线程管理与完善的硬件生态。Arduino / ESP32 适合快速原型验证，而这个项目重点实践多任务并发、I²C 互斥锁、可配置任务栈和条件编译；直接与一套完整嵌入式操作系统打交道，在系统思维上收获更大。

开发一共用了多长时间？

总计约 6 周：约 2 周聚焦嵌入式端（驱动适配、多线程与 MQTT），约 3 周负责 HarmonyOS 应用（从旧版 JavaUI API7 彻底重写至 ArkTS API23、从零实现 MQTT 客户端并接入 HDS 视觉），最后 1 周用于全链路联调测试与撰写报告；其中旧代码彻底迁移重写耗费了最多时间。

最大的技术挑战是什么？

最棘手的是 I²C 总线冲突：AHT20 和 SSD1306 共用同一条 I2C0，温湿度采集线程与显示刷新线程同时抢占读写时导致数据彻底错乱，靠 USB 逻辑分析仪抓取波形花了近两天才定位出根因，随后通过加互斥锁解决。其次则是用 ArkTS 从零手写完整 MQTT 客户端及断线重连与线程生命周期管理。

使用了哪些调试工具？

嵌入式侧主要依赖 USB 逻辑分析仪抓取 I²C 通信波形、UART0 串口打印日志以及 MQTTX 实时观察消息收发；HarmonyOS 侧主要结合 DevEco Studio 调试器、HiLog 系统日志与自研内置的 GlobalLogBus 面板，能实时观测 Broker 动向的 MQTTX 显著加快了联调速度。

这套项目能直接作为生产环境部署吗？

作为课程设计原型它已相当完整，但要真正用于农业生产落地还缺少几项生产特性：MQTT 鉴权密码机制、智能模式阈值的非易失持久化存储（当前存于内存），以及配网界面（当前 Wi-Fi SSID 与密码写死在代码中）；硬件方面 Hi3861 不具备工业级防护与传感器精细标定。但整体分层与协议架构是扎实的。

通过这个项目收获了什么？

收获远超单一语言本身：技术上串联了嵌入式驱动、RTOS、IoT 协议与移动应用前端；工程方法上深刻体会到“复杂度必须依靠分层架构管理”，从早期把逻辑塞入单文件陷入泥潭，到彻底按 common / modules / boards 与 Stage 模型拆分后变得清晰可预期；更重要的则是面对硬件玄学 bug 时的排查耐心。

一个从零到一的完整历程

从写下第一行代码到最终课程答辩，SmartShed 是一次横跨 OpenHarmony 与 HarmonyOS 生态的全链路实践，几乎触达了物联网系统的每一层：外设驱动、实时内核、网络通信、跨形态客户端以及 GN / Ninja 构建工程。

如果只挑一条最重要的工程体会，那就是系统复杂度要依靠清晰架构来化解——前期把逻辑堆砌在一起曾带来难以维护的困境，直到嵌入式拆出 common / modules / boards 且应用侧完全切换为分层 Stage 模型之后，每次迭代和联调才变得从容且可预期。

所有嵌入式固件与 HarmonyOS 客户端代码均已开源在 GitHub，欢迎查阅交流。
